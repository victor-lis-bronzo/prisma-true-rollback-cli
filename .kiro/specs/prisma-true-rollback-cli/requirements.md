# Requirements Document

## Introduction

Prisma ORM follows a strict "roll forward" migration philosophy and offers no practical native support for reverting (rolling back) migrations. When an engineer applies a migration in a development environment and later discovers a modeling flaw, the native workflow forces the creation of a *new* corrective migration. This pollutes the repository history and the CI/CD pipeline with error-and-correction files that are executed needlessly in downstream environments, and it degrades local development fluidity.

The **Prisma True Rollback CLI** (hereafter the **CLI**) is an unofficial command-line extension to the Prisma ecosystem, built with TypeScript and Node.js. It performs a *true*, destructive rollback in development environments by completely erasing the trace of an unwanted migration from both the database and the project's file system. To do this without corrupting Prisma's migration tracking, the CLI autonomously orchestrates a fixed sequence of steps: generating a reverse SQL script via Prisma's own engine, applying that script to the database, removing the migration record from Prisma's tracking table, and physically deleting the migration folder.

Because the operation is destructive and irreversible in intent, the CLI is designed exclusively for development environments and includes explicit safeguards, atomic execution guarantees, and compensating recovery so that a partial failure never leaves the project in an inconsistent state.

## Glossary

- **CLI**: The Prisma True Rollback command-line tool defined by this specification, invoked from a terminal (for example via `npx`).
- **Target_Migration**: The single Prisma migration selected by the User to be rolled back, identified by its migration name (the timestamped folder name under `prisma/migrations/`).
- **User**: The developer who invokes the CLI from a terminal in a local development environment.
- **Migrations_Directory**: The `prisma/migrations/` directory within the User's project that stores one folder per applied migration.
- **Migration_Folder**: The folder under the Migrations_Directory whose name corresponds to the Target_Migration and which contains its `migration.sql` file.
- **Tracking_Table**: The `_prisma_migrations` table maintained by Prisma in the target database to record applied migrations.
- **Reverse_SQL**: The SQL script generated by the CLI that undoes the schema changes introduced by the Target_Migration, transforming the current database schema back to the state that preceded the Target_Migration.
- **Prisma_Engine**: The Prisma CLI/engine binary invoked by the CLI as a child process (for example `prisma migrate diff`) to compute schema differences.
- **Database**: The relational database referenced by the User's Prisma configuration against which migrations are applied.
- **Rollback_Operation**: The complete, ordered sequence of steps the CLI performs to roll back the Target_Migration.
- **Compensating_Recovery**: The set of actions the CLI performs to restore the pre-Rollback_Operation state when a step fails after prior steps have already made changes.
- **Production_Indicator**: Any configured signal (for example a `NODE_ENV` value of `production`, or a production-designated connection target) that identifies a non-development environment.
- **Override_Flag**: An explicit command-line flag supplied by the User that authorizes the CLI to proceed when the environment cannot be determined as a development environment.
- **Pre_Operation_Snapshot**: The captured record of the pre-Rollback_Operation state, consisting of the Tracking_Table record for the Target_Migration and the complete Migration_Folder contents, used by Compensating_Recovery to restore the prior state.

## Requirements

### Requirement 1: Invoke Rollback for a Target Migration

**User Story:** As a developer, I want to invoke the CLI from my terminal and specify which migration to roll back, so that I can revert an unwanted migration without manually editing the database or file system.

#### Acceptance Criteria

1. WHEN the User invokes the CLI with exactly one Target_Migration name argument, THE CLI SHALL start a Rollback_Operation for that Target_Migration.
2. IF the User invokes the CLI without specifying a Target_Migration name, THEN THE CLI SHALL terminate with exit code 1, perform no changes to the database or file system, and display an error message that identifies the missing migration-name argument.
3. IF the User invokes the CLI with more than one Target_Migration name argument, THEN THE CLI SHALL terminate with exit code 1, perform no changes to the database or file system, and display an error message that reports only one migration name is accepted per invocation.
4. IF the specified Target_Migration name does not match any Migration_Folder in the Migrations_Directory, THEN THE CLI SHALL terminate with exit code 1, perform no changes to the database or file system, and display an error message that reports the unknown migration name.
5. IF the specified Target_Migration name does not have a corresponding record in the Tracking_Table, THEN THE CLI SHALL terminate with exit code 1, perform no changes to the database or file system, and display an error message that reports the migration is not recorded as applied.
6. IF the specified Target_Migration is not the most recently applied migration recorded in the Tracking_Table, THEN THE CLI SHALL terminate with exit code 1, perform no changes to the database or file system, and display an error message that reports only the most recently applied migration can be rolled back.
7. WHERE the User supplies a flag requesting the CLI version, THE CLI SHALL display the CLI version string and terminate with exit code 0 without starting a Rollback_Operation.

### Requirement 2: Development-Environment Safeguards

**User Story:** As a developer, I want the CLI to refuse to run against non-development environments, so that I do not accidentally destroy data in staging or production.

#### Acceptance Criteria

1. IF a Production_Indicator (defined as NODE_ENV set to "production" OR a connection target designated as production) is detected for the current invocation, THEN THE CLI SHALL terminate with a non-zero exit code and display an error message indicating that the Rollback_Operation is blocked outside development environments, without making any change to the Database or file system.
2. IF the environment cannot be determined (NODE_ENV is unset, empty, or unrecognized AND the connection target designation is absent) AND no explicit override flag is supplied, THEN THE CLI SHALL terminate with a non-zero exit code and display an error message indicating that the environment is ambiguous and an explicit override is required, without making any change to the Database or file system.
3. WHEN the CLI starts a Rollback_Operation, THE CLI SHALL display the Target_Migration name and a warning that describes the destructive and irreversible nature of the operation before making any change to the Database or file system.
4. WHILE running in interactive mode, THE CLI SHALL require the User to provide explicit confirmation before making any change to the Database or file system.
5. IF the User declines the confirmation prompt within 60 seconds, OR no response is received within 60 seconds, THEN THE CLI SHALL terminate with a zero exit code without making any change to the Database or file system.
6. WHERE the User supplies a non-interactive confirmation flag, THE CLI SHALL proceed with the Rollback_Operation without displaying an interactive confirmation prompt.

### Requirement 3: Reverse SQL Generation

**User Story:** As a developer, I want the CLI to generate the reversal SQL using Prisma's own engine, so that the reversal accurately reflects Prisma's understanding of the schema change.

#### Acceptance Criteria

1. WHEN the Rollback_Operation reaches the reverse-SQL generation step, THE CLI SHALL invoke the Prisma_Engine as a child process to compute the Reverse_SQL that transforms the current Database schema to the schema state preceding the Target_Migration.
2. IF the Prisma_Engine child process exits with a non-zero status during Reverse_SQL generation, THEN THE CLI SHALL terminate the Rollback_Operation, exit with a non-zero exit code, make no change to the Database or file system, and display an error message that includes the complete Prisma_Engine error output.
3. IF the Reverse_SQL script produced by the Prisma_Engine contains zero executable SQL statements (an empty script or a script consisting only of whitespace and SQL comments), THEN THE CLI SHALL terminate the Rollback_Operation, exit with a non-zero exit code, and display an error message reporting that no reversal statements were generated.
4. WHERE the User supplies a dry-run flag, THE CLI SHALL display the complete generated Reverse_SQL and terminate with a zero exit code without making any change to the Database or file system.
5. IF the Prisma_Engine child process does not complete within 30 seconds of being invoked, THEN THE CLI SHALL terminate the child process, terminate the Rollback_Operation, exit with a non-zero exit code, make no change to the Database or file system, and display an error message indicating that Reverse_SQL generation timed out.
6. IF the Prisma_Engine binary cannot be located or is not installed when the CLI attempts to invoke it, THEN THE CLI SHALL terminate the Rollback_Operation, exit with a non-zero exit code, and display an error message indicating that the Prisma_Engine binary was not found.

### Requirement 4: Atomic Database Reversion

**User Story:** As a developer, I want the database schema changes and tracking-table cleanup to be applied atomically, so that a failure midway does not leave the database in an inconsistent state.

#### Acceptance Criteria

1. WHEN the Rollback_Operation applies changes to the Database, THE CLI SHALL execute the Reverse_SQL and the removal of the Target_Migration record from the Tracking_Table within a single database transaction.
2. WHEN the Reverse_SQL executes successfully within the transaction, THE CLI SHALL remove the record whose migration name equals the Target_Migration from the Tracking_Table within the same transaction.
3. WHEN all database statements in the transaction complete successfully, THE CLI SHALL commit the transaction and terminate the Rollback_Operation with a zero exit code.
4. IF any statement within the database transaction fails, THEN THE CLI SHALL roll back the transaction so that the Database schema and Tracking_Table are restored to the exact state they held before the transaction began, with no partial changes persisted.
5. IF the transaction is rolled back due to a failure, THEN THE CLI SHALL terminate the Rollback_Operation with a non-zero exit code and display an error message that identifies the failing database statement and the underlying failure reason.
6. WHERE the target Database engine does not support transactional DDL, THE CLI SHALL, before executing any Reverse_SQL, terminate the Rollback_Operation with a non-zero exit code and display an error message indicating that atomic reversion is not supported for the engine, leaving the Database schema and Tracking_Table unchanged.

### Requirement 5: File System Cleanup

**User Story:** As a developer, I want the CLI to physically delete the reverted migration folder, so that the repository history no longer contains the unwanted migration.

#### Acceptance Criteria

1. WHEN the database transaction has been committed successfully, THE CLI SHALL, before deleting the Migration_Folder, create a snapshot of the complete Migration_Folder contents sufficient to reconstruct it during Compensating_Recovery.
2. WHEN the Migration_Folder snapshot has been created successfully, THE CLI SHALL delete the Migration_Folder corresponding to the Target_Migration, including all of its files and subdirectories, from the Migrations_Directory.
3. IF the Migration_Folder does not exist at the deletion step, THEN THE CLI SHALL treat the deletion as already satisfied, display a message reporting the folder was already absent, and continue the Rollback_Operation.
4. IF creation of the Migration_Folder snapshot or deletion of the Migration_Folder fails (including due to file-permission errors), THEN THE CLI SHALL initiate Compensating_Recovery to restore the Database changes made during the Rollback_Operation, display an error message that includes the underlying cause, and terminate with a non-zero exit code.
5. WHEN the Migration_Folder is deleted successfully, THE CLI SHALL display a message that confirms the Target_Migration was fully rolled back.
6. WHEN the Rollback_Operation completes successfully, THE CLI SHALL terminate with a zero exit code.

### Requirement 6: Compensating Recovery on Partial Failure

**User Story:** As a developer, I want the CLI to restore the previous state if the rollback fails after some steps have completed, so that I am never left with a half-reverted project.

#### Acceptance Criteria

1. WHEN the CLI is about to perform its first destructive action of the Rollback_Operation, THE CLI SHALL first capture a pre-operation snapshot consisting of the Tracking_Table record for the Target_Migration and the complete Migration_Folder contents.
2. IF capturing the pre-operation snapshot fails, THEN THE CLI SHALL terminate the Rollback_Operation with a non-zero exit code, make no destructive change, and display an error message reporting that the recovery snapshot could not be captured.
3. WHEN a step of the Rollback_Operation fails after at least one destructive action has been performed, THE CLI SHALL initiate Compensating_Recovery.
4. WHEN Compensating_Recovery is initiated, THE CLI SHALL restore the Database schema and the Tracking_Table record for the Target_Migration to the values captured in the pre-operation snapshot.
5. WHEN Compensating_Recovery is initiated, THE CLI SHALL restore the Migration_Folder contents for the Target_Migration so that they are byte-for-byte identical to the pre-operation snapshot.
6. WHEN Compensating_Recovery has restored the Database, Tracking_Table, and Migration_Folder to match the pre-operation snapshot, THE CLI SHALL terminate with exit code 1 and display a message reporting that the Rollback_Operation was aborted and the prior state was restored.
7. IF Compensating_Recovery does not fully restore the prior state to match the pre-operation snapshot, THEN THE CLI SHALL terminate with exit code 1 and display a message that lists each element that was not restored and the specific manual steps required to restore consistency.

### Requirement 7: Database Compatibility and Connection Handling

**User Story:** As a developer, I want the CLI to connect to my Prisma-configured database and support the database engines I use, so that the rollback runs against the correct target.

#### Acceptance Criteria

1. WHEN the CLI starts a Rollback_Operation, THE CLI SHALL resolve the Database connection target by reading the datasource block from the User's schema.prisma file and the DATABASE_URL environment variable.
2. IF the schema.prisma file cannot be located or the connection target cannot be resolved because the DATABASE_URL environment variable is unset or empty, THEN THE CLI SHALL terminate with exit code 1 and display a message that identifies the missing configuration source.
3. WHEN the CLI attempts to establish the Database connection, THE CLI SHALL apply a connection timeout of 10 seconds.
4. IF the Database connection cannot be established within the 10-second timeout, THEN THE CLI SHALL terminate with exit code 1, display a message that reports the connection failure and the resolved target host, and make no changes to the Database.
5. IF the resolved Database engine is not one of PostgreSQL, MySQL, or SQLite, THEN THE CLI SHALL terminate with exit code 1 and display a message that names the unsupported engine and lists the supported engines PostgreSQL, MySQL, and SQLite.
6. WHEN the Rollback_Operation terminates for any reason, THE CLI SHALL close any Database connection it opened.

### Requirement 8: Operational Feedback and Logging

**User Story:** As a developer, I want clear step-by-step feedback during the rollback, so that I understand what the CLI did and can diagnose failures.

#### Acceptance Criteria

1. WHEN the CLI begins each step of the Rollback_Operation, THE CLI SHALL display a message to standard output that identifies the step by name and its position in the sequence (e.g., "Step 2 of 5: <step name>").
2. WHEN a step of the Rollback_Operation completes successfully, THE CLI SHALL display a message to standard output that identifies the completed step by name and indicates successful completion.
3. IF any step of the Rollback_Operation fails, THEN THE CLI SHALL display a message to standard error that identifies the failing step by name, includes the underlying error detail, and indicates that the Rollback_Operation was aborted with a non-zero exit code.
4. WHERE the User supplies a verbose flag, THE CLI SHALL display each executed database statement and the invoked Prisma_Engine command with all connection credentials (including the DATABASE_URL value, username, password, host, and port) replaced by a fixed redaction placeholder.
5. THE CLI SHALL exclude connection credentials (including the DATABASE_URL value, username, password, host, and port) from every message it displays to standard output and standard error, replacing them with a fixed redaction placeholder.
